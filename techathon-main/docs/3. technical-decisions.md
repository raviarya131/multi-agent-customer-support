# Technical Decisions

Architecture Decision Record (ADR) summary for the Multi-Agent Support Engine.

**Docs chain:** [`README.md`](README.md) → [`architecture.md`](architecture.md) → [`hld.md`](hld.md) → **technical-decisions.md** → [`lld.md`](lld.md)

## ADR-001 — Three-service monorepo split

| | |
|---|---|
| **Context** | Need clear boundaries between UI, persistence/HITL, and AI pipeline for team parallel work and demo clarity. |
| **Decision** | `apps/web` + `apps/api` + `apps/agent` as separate Node processes in one npm workspace. |
| **Alternatives** | Single Express app serving UI + API + agents — rejected: couples release cycles and obscures agent isolation. |
| **Consequences** | HTTP-only integration; types duplicated per service (`web/lib/types` vs `agent/contracts/types`). Deployment is three ports, one `npm run dev:all`. |

---

## ADR-002 — LangGraph with linear fallback

| | |
|---|---|
| **Context** | Hackathon rubric asks for LangGraph; demos must not fail if graph loader breaks. |
| **Decision** | Primary runner: `@langchain/langgraph` `StateGraph`. Fallback: `pipeline.ts` runs identical 8 steps sequentially. |
| **Alternatives** | CrewAI / AutoGen — rejected: Python-only, would split stack. LangGraph-only — rejected: single load failure kills demo. |
| **Consequences** | Two code paths to maintain; same `PipelineState` contract keeps them aligned. |

---

## ADR-003 — SQLite via `node:sqlite`

| | |
|---|---|
| **Context** | Judges need zero-install demo on Windows; avoid native module builds. |
| **Decision** | Node 22 built-in `node:sqlite` — no `better-sqlite3`, no Postgres setup. |
| **Alternatives** | PostgreSQL — rejected for demo friction. In-memory only — rejected: loses audit across restarts. |
| **Consequences** | Not horizontally scalable; fine for hackathon. Schema in `db/schema.ts` with incremental migrations. |

---

## ADR-004 — Single LLM gateway (`callLLM`)

| | |
|---|---|
| **Context** | Company endpoint is OpenAI-compatible; may switch to Azure/Groq for judging environment. |
| **Decision** | One `shared/gateway/index.ts` with provider adapters; pipeline steps never import vendor SDKs directly. |
| **Alternatives** | Per-step SDK calls — rejected: no hot-switch, harder to mock. |
| **Consequences** | All LLM calls logged with `traceId`; retries centralized; JSON parsing normalized. |

---

## ADR-005 — Deterministic fallback on every LLM step

| | |
|---|---|
| **Context** | Demo must work without API keys; judges score what runs live. |
| **Decision** | Classifier → keywords; sentiment → heuristics; decompose → clause scoring; agents → KB/tool templates; synthesize → merge template. |
| **Alternatives** | Fail closed on missing key — rejected: brittle demos. |
| **Consequences** | Offline mode is first-class; `audit_trail.kind` records `llm` vs `heuristic` honestly. |

---

## ADR-006 — Declarative JSON use cases for specialists

| | |
|---|---|
| **Context** | Five domains × multiple intents; rubric rewards swappable agents in &lt;30 lines. |
| **Decision** | Each use case = JSON (`prompt`, `tools`, `knowledge_base`, `example_utterances`). `makeDeclarativeHandler()` runs all. |
| **Alternatives** | Code-per-intent handlers — rejected: every new intent needs deploy. |
| **Consequences** | Platform can CRUD use cases; `agent.reload()` swaps registry atomically. Prompt quality depends on JSON authoring. |

---

## ADR-007 — KB retrieval (not vectors)

| | |
|---|---|
| **Context** | Need grounded answers without embedding server dependency. |
| **Decision** | `retrieveFromScope()` scores markdown sections by TF-IDF; broad queries return all matching sections. |
| **Alternatives** | pgvector / Pinecone — rejected: infra overhead for demo. Whole-doc dump — rejected: context overflow. |
| **Consequences** | Fast, offline-capable; `retrieveFromScope` signature unchanged if vectors added later. |

---

## ADR-008 — In-process mock tools

| | |
|---|---|
| **Context** | Original system design showed separate billing/technical services. |
| **Decision** | Shared tool pool (`orderLookup`, `dbQuery`, …) with in-memory mock data keyed by `customerId`. |
| **Alternatives** | Separate Express mock services — rejected: three extra processes for same data. |
| **Consequences** | Swap `tool.run()` for real HTTP; use case JSON unchanged. Same demo data across team (`cust_001` …). |

---

## ADR-09 — Live config store pattern

| | |
|---|---|
| **Context** | Admin panel must edit policies, agents, FAQ, KB without redeploy. |
| **Decision** | `runtime-config/*.json` + Zod validation + in-memory cache + explicit `reload()` / `invalidateCache()`. |
| **Alternatives** | DB-backed config — rejected: overkill; files are git-diffable and easy to seed. |
| **Consequences** | Changes apply on next request; config audit log in API SQLite. Guard signals merge defaults + file (new phrases appear without wiping admin edits). |

## ADR-010 — Severity from agent findings, not customer tone

| | |
|---|---|
| **Context** | Angry wording alone should not auto-P1 every ticket. |
| **Decision** | `runSeverity()` keyword-matches **agent report blob** (findings, evidence, reasoning). Sentiment only nudges priority (+1 angry, capped). |
| **Alternatives** | Sentiment-driven severity — rejected: inflates priority on frustrated but solvable issues. |
| **Consequences** | Word-boundary matching prevents false positives (e.g. "pin down" ≠ outage). Unresolved **investigation** floors to medium, not single-agent KB gap. |

---

## ADR-011 — Escalation gate design (meaningful HITL)

| | |
|---|---|
| **Context** | Early builds escalated on every `needs_info` or mixed partial result — noisy and wrong for demos. |
| **Decision** | Six togglable rules in `policies.json`. Key refinements: (1) hard guard always escalates; (2) **productive partial** (one agent resolved) suppresses conflict escalation; (3) frustration escalates only on **repeat contact still blocked** or **total first-contact failure**; (4) hard signals skip multi-domain decompose → policy `escalate_to_human` only. |
| **Alternatives** | Escalate on any unresolved agent — rejected: KB gaps ≠ human needed. |
| **Consequences** | Security/legal/sue threats route correctly; routine policy lookups stay self-serve. |

---

## ADR-012 — Evidence and reasoning traceability in synthesis

| | |
|---|---|
| **Context** | Rubric: "every resolution must include reasoning"; "all agent interactions logged". |
| **Decision** | Synthesizer LLM may rewrite `summary` / `findings` / `actions` for customer voice; `reasoning` and `evidence` always copied from agent reports, never model-invented. Prior-turn clarification actions not inherited when current turn has fresh findings. |
| **Alternatives** | Full LLM rewrite including evidence — rejected: fabrication risk. |
| **Consequences** | Trace viewer shows provenance; occasional UX polish needed (store voice guardrails). |

---

## ADR-013 — FAQ before classifier LLM

| | |
|---|---|
| **Context** | Greetings and FAQs should not burn LLM tokens or spawn specialists. |
| **Decision** | `matchFaq(message)` in classify node before LLM; category `faq` short-circuits to canned answer. Greetings/out-of-scope similarly skip fan-out. |
| **Alternatives** | LLM-only classification — rejected: cost + inconsistency for trivial inputs. |
| **Consequences** | Platform FAQ tab is operationally important; match modes: contains / exact / regex. |

---

## ADR-014 — Frontend: Next.js 15 + shadcn dark theme

| | |
|---|---|
| **Context** | Need professional ops console + streaming chat quickly. |
| **Decision** | Next.js App Router, shadcn/ui, Claude-inspired dark theme, client islands for interactive pages. |
| **Alternatives** | CRA — rejected: weaker routing/layout. Light-only theme — rejected per product preference. |
| **Consequences** | `Suspense` boundaries where needed (`useSearchParams`); SSE via fetch not EventSource for POST. |

---

## ADR-015 — Channel-agnostic intake (integration deferred)

| | |
|---|---|
| **Context** | Stretch goal mentions Zendesk/Linear/Jira; timeboxed to core engine. |
| **Decision** | `POST /api/tickets` accepts `{ message, customer_id?, ticket_id? }` — any channel adapter is a thin webhook → same endpoint. |
| **Alternatives** | Build Zendesk integration first — rejected: core rubric points come from agent quality. |
| **Consequences** | Documented in README roadmap; no pipeline changes needed for email/Slack/Zendesk later. |

## Known limitations (accepted trade-offs)

| Limitation | Mitigation path |
|------------|-----------------|
| Mock tools | Replace `run()` implementations |
| TF-IDF retrieval | Plug embeddings behind `retrieveFromScope` |
| Single-node SQLite | Postgres + connection pool |
| No automated tests | CLI `step` / `pipeline` for manual regression |
| Email optional | In-app notifications always on |
