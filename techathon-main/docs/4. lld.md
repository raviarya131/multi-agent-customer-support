## 3. PipelineState — the shared state object

All 8 pipeline steps read and write a single `PipelineState` object. Each step
only writes its own fields; it never deletes another step's fields.

```typescript
interface PipelineState {
  // input
  run_id:        string
  message:       string
  ticket_id:     string
  customer_id?:  string
  message_count: number
  history:       Message[]          // prior turns on this ticket
  prior_context? PriorRunContext    // resolution + findings from last run

  // step outputs (appended as each step runs)
  guard?:         Guard             // force_escalation, matched_phrase, reason
  classification? Classification   // primary_intent, intents[], is_multi_issue, fallback, category, faq_answer?
  sentiment?:     Sentiment         // label, score, frustration, drivers[], trend
  sub_problems?:  SubProblem[]      // id, domain, description (one per parallel agent)
  agent_reports?: AgentReport[]     // findings[], actions[], reasoning, evidence[], confidence, duration_ms
  investigation?  Investigation     // overall_status, conflicts[]
  severity?:      Severity          // level, priority, reasoning
  escalation?:    Escalation        // escalate, recommended_team, urgency, assigned_agent, reason
  resolution?:    Resolution        // summary, findings[], actions[], reasoning, evidence[]

  audit_trail:    AuditEvent[]      // grows with every step
}

interface AuditEvent {
  step:      string
  actor:     string
  summary:   string
  detail?:   string
  kind:      "llm" | "heuristic" | "rule"
  timestamp: string
}
```

## 4. Agent pipeline — step-by-step 

### 4.1 Guard

```
Input:  message
Output: guard { force_escalation, matched_phrase?, reason }
Kind:   rule (regex match, no LLM)
Config: policies.json → guard.signals[] (phrase, enabled)
```

If `force_escalation = true` the escalation gate later **always** escalates,
regardless of severity or investigation outcome.

### 4.2 Classifier

```
Input:  message, history
Output: classification { primary_intent, intents[], is_multi_issue, fallback, category, faq_answer?, faq_label? }
Kind:   LLM → keyword fallback

FAQ short-circuit: matchFaq(message) runs first.
  If matched → classification.category = "faq"; skip LLM call entirely.

LLM call:
  system = GUARDRAILS_BLOCK + dynamic prompt (lists all domain agents + their descriptions)
  user   = conversation history (last 4 turns) + current message
  output = { category, intents[{ type, confidence }], is_multi_issue }
  temp   = 0  (deterministic routing)

Fallback (no provider / error):
  TF-IDF keyword scorer over domain keyword lists (from agents.json)
```

### 4.3 Sentiment

```
Input:  message, history
Output: sentiment { label, score, frustration, drivers[], trend }
Kind:   LLM → heuristic fallback

LLM call:
  system = GUARDRAILS_BLOCK + sentiment prompt
  user   = last 8 turns (customer + support) + current message
  output = { label, score, frustration, drivers[], trend }
  temp   = 0

Heuristic fallback:
  Score current message (angry words, frustrated words, caps, exclamations)
  Score prior customer turns → detect repeat-contact frustration
  trend = current score vs prior avg (±0.15 threshold)
```

### 4.4 Decomposer

```
Input:  message, classification, guard? (force_escalation)
Output: sub_problems[] — one per domain that needs investigation
Kind:   LLM → heuristic fallback

Hard-signal shortcut (nodes.ts):
  if guard.force_escalation → single SP-1 domain=policy, description=message
  (skips multi-domain split; routes to escalate_to_human use case)

Single-intent: [{ id: "SP-1", domain: primary_intent, description: message }]
Multi-intent:  one SP per intent above threshold (policies.json intents.*)

LLM call:
  system = GUARDRAILS_BLOCK + dynamic prompt (domain list + descriptions)
  user   = message + classification JSON
  output = [{ id, domain, description }]

Heuristic fallback:
  Domain keyword TF-IDF per clause (sentence-split by "and/also/plus/,")
```

### 4.5 Orchestrator / Investigate

```
Input:  sub_problems[], message, history, prior_context?
Output: agent_reports[], investigation { overall_status, conflicts[] }
Kind:   LLM per agent (inside each specialist)

Fan-out:
  Promise.all(sub_problems.map(sp => getAgent(sp.domain).run(sp, context)))
  Each returns AgentReport { findings[], actions[], reasoning, evidence[], confidence, duration_ms }

Merge:
  overall_status = "resolved" if all resolved
                   "partial"  if mixed
                   "unresolved" if all failed/unresolved
  conflicts = agent pairs that contradict each other (on refund/charge amounts etc)

getAgent(domain):
  1. Check AGENT_REGISTRY (built-in hard-coded agents)
  2. Check runtime custom agents (materialized from agents.json at boot)
  3. Return policy fallback agent if unknown domain
```

### 4.6 Severity

```
Input:  agent_reports[], investigation, sentiment, message_count
Output: severity { level, priority, reasoning }
Kind:   rule (no LLM)

level from findings keywords (word-boundary match via blobMatches):
  high   = "locked", "breach", "security", "outage", "service down", …
  medium = "refund", "charge", "payment", "duplicate", …
  low    = default
  override: investigation.overall_status === "unresolved" AND level low → medium
  NOTE: single agent unresolved on a partial ticket does NOT force high

priority = base[level] + modifiers:
  +1 angry sentiment (skipped on productive partial)
  +1 repeat contact (message_count > 1)
  +1 conflicts detected (skipped on productive partial)
  cap at 3 → P1/P2/P3
```

### 4.7 Escalation

```
Input:  guard, investigation, severity, sentiment, agent_reports, message_count
Output: escalation { escalate, reasons[], recommended_team, urgency, assigned_agent, internal_actions, reason }
Kind:   rule gate → LLM handoff plan → deterministic fallback

Gate (shouldEscalate) — each rule toggled in policies.json:
  hard_guard         → guard.force_escalation (always)
  high_severity      → severity.level === "high"
  unresolved         → investigation.overall_status === "unresolved" (all agents failed)
  conflicts          → conflicts.length > 0 AND NOT productive partial
  specialist_handoff → any unresolved agent AND investigation fully unresolved
  frustration_repeat → (repeat AND frustrated AND not resolved)
                       OR (first contact AND frustrated AND fully unresolved AND none resolved)

productive partial = overall_status "partial" AND at least one agent_report.status === "resolved"

Team routing: teamByDomain(primary_intent) → department
API-side: pickAssignee(dept, countOpenByAssignee()) — least-load balancing

LLM handoff plan:
  system = GUARDRAILS_BLOCK + escalation prompt
  user   = all agent reports + severity reasoning + KB: escalation_matrix.md
  output = { recommended_team, urgency, reason, internal_actions[], handoff_summary }
```

### 4.8 Synthesizer

```
Input:  agent_reports[], escalation, classification (category), faq_answer?
Output: resolution { summary, findings[], actions[], reasoning, evidence[] }
Kind:   LLM → template fallback

Category shortcuts (no LLM):
  "greeting"    → greetingResolution()
  "faq"         → faqResolution(faq_answer)
  "out_of_scope"→ outOfScopeResolution()

"support" path:
  Template merge: flatten all agent findings/actions/evidence, deduplicate
  LLM call (temp 0.3, maxTokens 700):
    system = GUARDRAILS_BLOCK + "merge into one empathetic reply" prompt
    user   = merged template + each agent's reasoning
    output = { summary, findings[], actions[], reasoning, evidence[] }
  Reasoning + evidence come from agents — never LLM-invented
```

## 5. Declarative agent framework

Each specialist agent is a JSON-configured framework agent. No code per use case.

```
agents/<domain>/
├── index.ts          createAgent({ name, useCasesDir: "./usecases" })
└── usecases/
    ├── use_case_a.json
    └── use_case_b.json
```

**Use case JSON schema:**
```json
{
  "id": "order_tracking",
  "description": "Customer wants to know where their order is",
  "example_utterances": ["where is my order", "track my package"],
  "prompt": "You are the Orders specialist. Investigate the order status...",
  "tools": [{ "name": "orderLookup" }],
  "knowledge_base": [{ "knowledge_file": "shipping_delivery.md" }]
}
```

**Runtime flow inside an agent (`declarative.handler.ts`):**
```
1. Route sub-problem to best-matching use case (embedding score or keyword match)
2. Gather KB snippets: retrieveFromScope(query, kbScope) → TF-IDF over library/*.md
3. Run tools: toolRegistry.run(toolName, args) → structured mock data
4. Assemble LLM prompt:
     system = GUARDRAILS_BLOCK + use_case.prompt + "KB SNIPPETS: ..." + "TOOL RESULTS: ..."
     user   = sub-problem description + customer history
5. callLLM({ system, user, json: true, temperature: 0.2 })
6. Return AgentReport
```

## 7. Real-time transport

### Pipeline streaming (customer chat)

```
Client → POST /api/tickets/stream
       ← text/event-stream
         data: {"type": "progress", "step": "classify", ...}
         data: {"type": "step_done", "step": "classify", "snapshot": {...}}
         data: {"type": "agent_done", "agent": "billing"}
         data: {"type": "done", "state": {...}}
```

Implemented with `ReadableStream` + `fetch` (not `EventSource`) so the request
can carry a POST body and Authorization header.

### Collaboration feed (Team dashboard)

```
Client → GET /api/collab/stream?token=<bearer>
       ← text/event-stream
         data: {"type": "ping", "ts": "..."}   (every 25s, keep-alive)
         data: {"type": "escalation_created", "activity": {...}}
         data: {"type": "agent_reply", "activity": {...}}
         data: {"type": "escalation_handoff", "activity": {...}}
         data: {"type": "escalation_resolved", "activity": {...}}
         data: {"type": "case_note", "note": {...}, "activity": {...}}
         data: {"type": "presence", "agent_id": "...", "online": true}
```

Token carried in query string because `EventSource` cannot set headers.
Clients fall back to polling every 20s on reconnect.

## 9. Sentiment pipeline detail

```
analyzeSentiment(message, history, traceId):
  1. heuristic = runSentiment(message, history)   -- always runs, result used as fallback
  2. if no LLM provider → return heuristic
  3. callLLM({ system, user: buildConversationPrompt(message, history[-8:]) })
     → { label, score, frustration, drivers[], trend }
  4. Validate all fields; fill gaps from heuristic
  5. Return enriched Sentiment

heuristic runSentiment(message, history):
  scoreMessage(text) → { score, drivers }
    angry words → +0.6
    frustrated words → +0.4
    exclamations → +0.1 each (cap 0.3)
    ALL-CAPS words → +0.1 each (cap 0.3)
  priorScores = history.customerTurns.map(scoreMessage)
  if priorScores.length > 0 AND (any prior score > 0.35 OR current > 0.35):
    score += 0.15 (repeat-contact frustration nudge)
  trend = current vs priorAvg (rising / steady / easing)
  label = score >= 0.7 → "angry" | >= 0.35 → "frustrated" | else "neutral"
  frustration = label !== "neutral" OR score >= 0.35
```

Exposed on: `TicketDashboardRow.sentiment/sentiment_score/frustration`,
`RunSessionRow.sentiment/sentiment_trend`, `SentimentBadge` component.

## 10. KB article generation pipeline

```
POST /api/platform/kb/suggest { ticket_id? OR source? }
  ↓
If ticket_id:
  getLatestRun(ticket_id) → PipelineState
  Assemble KbSource:
    question  = first customer message
    resolution = state.resolution.summary
    findings  = flatten agent_reports[].findings + resolution.findings (max 12)
    actions   = flatten agent_reports[].actions + resolution.actions (max 12)
    domain    = classification.primary_intent
  ↓
agentAdmin.generateKb(KbSource)
  ↓ (agent side)
generateKbArticle(src):
  if no LLM: templateDraft(src) → structured markdown from fields
  else:
    callLLM({ system: "write a KB article", user: KbSource fields })
    → { title, filename, content, summary }
    uniqueFilename(base) → check against existing library/*.md
  ↓
Return KbDraft { title, filename, content, summary, source: "llm"|"template" }

Admin reviews draft in editor → PUT /api/platform/kb/:file → writes to library/*.md
```

Draft is **never auto-saved**. Every save is an explicit admin action.

## 11. Auth model

```
Account { id, email, role: "user"|"agent"|"admin", name, customer_id?, agent_id? }

Sessions: bearer tokens in SQLite; resolved on every request via accountForToken()
Token extraction: Authorization header OR ?token= query param (for SSE EventSource)

Role gates:
  requireRole("user")        → customer chat, feedback
  requireRole("admin","agent") → escalation management, collab
  requireRole("admin")       → observability, platform config, dashboard
```

Agent accounts are created alongside human_agents entries. `account.agent_id`
links to `human_agents.id`, enabling per-agent case filtering and notifications.

## 12. Error handling and graceful degradation

| Scenario | Behaviour |
|----------|-----------|
| No LLM provider configured | Every step runs its deterministic fallback; pipeline completes |
| LLM call fails (after 2 retries) | Step logs error, returns heuristic result; `audit_trail` records `kind: "heuristic"` |
| LangGraph executor fails to load | `run.ts` catches and switches to identical linear runner (`pipeline.ts`) |
| Agent domain not in registry | Falls back to policy agent (safe catch-all) |
| Empty/whitespace message | API returns 400 before pipeline starts |
| Malformed JSON from LLM | Gateway strips fences and re-parses; throws if still invalid → heuristic path |
| Tool call fails | Agent continues without tool result; marks `evidence` accordingly |
| SSE client disconnects mid-stream | `req.on("close")` cleans up; partial state is discarded |
| Duplicate escalation on same ticket | `getOpenEscalationForTicket` guard prevents double-creation |
